Maintainer's Guide

This guide explains how every script and every function works, in plain English, so you can change things yourself without breaking the pipeline. It assumes no Python experience. Read parts 1 and 2 once; after that, use part 5 (recipes) and part 6 (golden rules) whenever you want to change something.

For maintainers

The one-minute picture

How the pipeline is structured

There are six Python files. Only two do the real work; the others are wrappers and tools.

You double-click "Run Daily Reconciliation"

1
Front Door
daily_runner.py
Finds the files in incoming/, decides folder names, archives inputs. Knows nothing about accounting.
2
Recipe Card
clean_pipeline.py
run_day(): the recipe card. Calls the pipeline_core functions in the right order, writes the outputs.
3
Engine
pipeline_core.py
The engine. Every rule about money lives here: reading files, the 4 cleaning rules, building the three journals, the balance checks.
⚙
Settings
reference/reference.json
The "settings file": shops, cost centres, journal row types, coupon codes. Plain text.

Side tools, used occasionally

  • combine_exports.py — stacks several days' exports into one import file.
  • extract_reference.py — rebuilds reference.json from a finished workbook.
  • validate_exports.py — compares one run's exports against another set.
A rule of thumb for where to look

If the change is about a shop, cost centre or coupon code, edit reference.json (no code at all). If it's about folders or file names, look in daily_runner.py. If it's about money, rules or journal content, look in pipeline_core.py.

Python survival kit

10 minutes to read this codebase

You only need five ideas to read this codebase.

1
A function is a named recipe

def read_banking(path): defines a recipe called read_banking that needs one ingredient (path, the file location). Everything indented below it is the recipe. return b at the end is what the recipe hands back. Indentation is not decoration in Python — it is the structure, so when editing, keep lines aligned exactly as their neighbours (4 spaces per level, never tabs).

2
A dictionary maps names to values

{'CG-BLA01': 'A52'} is a lookup table: ask for 'CG-BLA01', get 'A52'. ref['shop_cost_centre'] is such a table. .get(sh, NA) means "look up sh, and if it's not there, give me NA instead of crashing".

3
A DataFrame is a spreadsheet in memory

The variable names follow a convention throughout: s = the Sales sheet, si = Sales Items, sp = Sales Payments, each as a DataFrame. si['Total'] is a whole column. si.groupby('Sale ID')['Total'].sum() means "subtotal the Total column for each Sale ID" — exactly a pivot table. df[df['Type'] == 'POS Payment'] means "keep only the rows where Type is POS Payment" — exactly a filter.

4
f-strings build text from values

f'cash difference £{difference}' inserts the value of difference into the message. The {} parts are live; the rest is literal text you can reword freely.

5
Comments

Anything after # on a line is a note for humans, ignored by Python. The scripts are full of them — read them, they explain intent.

How to edit safely

Use a plain-text editor (Notepad++ or VS Code on Windows, TextEdit-in-plain-mode or VS Code on Mac — not Word). Before any change, copy the file you're editing to e.g. pipeline_core BACKUP.py. If a run crashes after your edit, the error message's last few lines name the file and line number — go there, compare with your backup.

3

The files, one by one

A tour of every script

daily_runner.py — the front door

find_one(patterns, kind, required) Utility
Looks in incoming/ for one file matching the patterns (e.g. *zettle*.csv). Refuses to guess if it finds two, tells you plainly if it finds none. If your file names change shape, this is where the matching patterns live.
main() Entry
Finds the four inputs, calls run_day(...), then moves results to output/<trading-date>/ (adding _run2, _run3 if you re-run a day) and the inputs to archive/<trading-date>/. If the pipeline crashes it prints the error and touches nothing.

clean_pipeline.py — the recipe card

One important function, run_day(...). Its steps, in order:

1
Read the four inputs (till workbook, Zettle CSV, banking CSV, coupons).
2
Work out the trading date from the Sales sheet and build the journal reference like SU 29.01.26. Flags for review if the till export spans more than one date.
3
Collect the coupon sale IDs (sales where Coupon Amount isn't zero).
4
Apply the cleaning rules: clean(...) then fix_negative_misc(...).
5
Derive the per-item Shop / Description / Payment Type columns.
6
Work out per-shop cash takings and per-shop coupon totals.
7
Build the three journals: build_ptf1_rows, build_banking_table + build_ptf2_rows, build_ptf3_rows.
8
Run balance_and_checks(...).
9
Only if balanced AND nothing in manual_review: write the three *_PTFn_export.csv files. Warnings do not block. Always writes the _CLEANED.xlsx workbook, run_report.json, and SUMMARY.txt.
What blocks exports

If you ever want to change what blocks exports, the line to find is:

if balanced and not report['manual_review']:

Anything appended to report['manual_review'] anywhere in the code blocks exports; anything appended to report['warnings'] is shown but does not.

pipeline_core.py — the engine

See Part 4.

combine_exports.py — batching for import

parse_date(s)
Understands dd/mm/yyyy and several other date shapes.
day_folder(day)
Finds output/<date>, preferring the highest _runN folder if the day was re-run.
day_frames(folder)
Loads that day's PTF1, PTF2, PTF3 CSVs.
main(argv)
Asks for the from/to dates, warns about missing days, stacks everything in order, writes output/PTF_<d1>-<d2>.csv in Windows (cp1252) encoding, and re-checks the combined file balances.

extract_reference.py

Reads only the Control sheet of a finished workbook and rewrites reference.json (shop→cost centre, the 8 PTF 2 row types, coupon→outlet). You will rarely need it — editing reference.json by hand is usually easier.

validate_exports.py

Terminal
python3 validate_exports.py --any-order <run_folder> <old csvs...>

Compares a run's exports against reference CSVs, cell by cell, tolerant of number formatting. Your safety net after code changes (see Part 7).

pipeline_core.py, function by function

The engine, dissected

The constants at the top

Python
TOL = 0.005            # "equal to the penny" tolerance everywhere
NA  = '#N/A'           # what an unknown shop's cost centre shows as
SUFFIX = {'VOUCHER': 'v', 'CASH': 'x', ...}
MOVE_PRIORITY = {'VOUCHER': 0, 'CASH': 1, 'IZETTLE': 2, 'CARD': 2}
R2 = # round to 2 decimal places (used constantly)

SUFFIX and MOVE_PRIORITY control the sale-splitting rule: when one sale was paid with two methods, the lowest priority method is moved out onto a new Sale ID ending in its suffix letter (voucher part → ...v, cash part → ...x), and the highest priority keeps the original ID. Card keeps the original ID whenever it's involved so Zettle matching still works.

Readers (files in)

read_till_workbook(path) Reader
Opens the till .xlsx (headers are on row 5, hence skiprows=4 inside) and returns the three DataFrames s, si, sp.
read_csv_any(path) Reader
Reads a CSV in whatever encoding it was saved in (Excel's Windows format, UTF-8, with/without BOM). All CSV readers use it.
money(series) Parser
Turns Excel-style money text into numbers: strips £, thousands commas, spaces; treats (5.00) as -5.00.
read_zettle(path) Reader
Keeps only Type == 'POS Payment' (and Completed), cleans Gross/Fee/Net with money, and pulls the till Sale ID out of the Item Title (the part before the first underscore).
read_banking(path) Reader
Needs Shop_Code and Cash_Banked; Float_Change (signed: +7 up, -5 down); Card_Settlement optional (blank = skip the cross-check). Old files with Float_Start/End or Cash_Coins still load.
read_coupons(path) Reader
Forgiving headers ('Coupon code' or 'Coupon_Code', 'amount' or 'Amount'); ignores extra columns like 'Number of times used'.

Cleaning (the 4 rules)

subset_for_amount(amounts, target) Solver
The puzzle-solver used by splitting: which combination of item lines adds up to the moved payment? Prefers whole lines; will split one line in two if it must.
clean(s, si, sp, report) Cleaner
Rules 1–3 in one pass:
  • Splits multi-payment sales (using SUFFIX / MOVE_PRIORITY above) and merges duplicate payments of the same method. Each action is logged into report['splits'] / report['merges'].
  • Deletes VOIDED sales that still carry a value (rows removed from all three sheets; logged in report['voids']).
  • Penny fixes: if a sale's items and payments disagree by 5p or less, nudges one item line so they match; more than 5p goes to manual_review.
fix_negative_misc(...) Rule 4
A negative MISC line is re-labelled to the product of the matching original sale (same shop, same payment type, same amount, nearest earlier sale with a single product). No match → manual_review.

Derived columns

derive_item_columns(si, sales, sp, coupon_ids, blank_desc_label) Builder
Adds three columns to Sales Items:
  • Shop — from the sale's Outlet Tag
  • Payment Type — CASH → 'Cash'; card entry mode ending 'EMV' → 'Card'; otherwise 'Redeemed'; coupon sales → 'Coupon'/'Split'
  • Description — product name for CG-/CL- shops, category for cafés; blank café categories become blank_desc_label, default '0'

Journal builders

Every journal row is a dictionary with keys 'H' to 'Z' — the 19 output columns, named after their old spreadsheet column letters. The ones you'll care about:

Key Meaning
JThe money value (always positive)
KNominal code
LNarrative
MCost centre
NDepartment
OShop
RSYSTraderTranType (4 or 5 for nominal lines, 1 for bank lines)
Y / ZDate and journal reference
build_ptf1_pivot(si_d) Builder
Subtotals Card+Cash items by Shop × Description, alphabetically.
eval_ptf1_row(...) Builder
Turns one subtotal into a PTF 1 row: nominal 4150 if the description ends 'Donation', 2710 for Pay-it-Forward, else 5000; VAT maths (P = J / 1.2 when VAT applies); R = 4 for positive, 5 for negative amounts.
eval_ptf1_donation_row(...) Builder
The two fixed rows at the top of PTF 1 (CG Network Donation → cost centre 153/GRO, General Donation → 100/CEN).
build_ptf1_rows(...) Builder
Glues the above together.
dept_of(shop) Utility
'GRO' if the code starts CG-, 'CLO' if CL-, else 'HEC'.
build_banking_table(...) Builder
One row of figures per shop (every shop in reference.json, plus any unexpected ones → manual_review): Card and Zettle Fee grouped from the Zettle CSV; Cash banked; Difference = Cash_Banked − cash payments + Float_Change (so float money isn't mistaken for a discrepancy); differences over £10 → warnings (do not block). Card_Settlement, when given, is cross-checked here.
build_ptf2_rows(bank_table, ref, ...) Builder
Expands each shop's figures into its 8 journal lines using ref['ptf2_row_types']. Bank lines (Card → 1980, Cash → 1990) get R = 1. Nominal lines get R = 4 when the underlying figure is positive, 5 when negative — which is what makes 'Float decreased' post as 4, 'Float increased' as 5, surplus differences 4, shortfalls 5, with J always positive.
build_ptf3_rows(sp, sales, coupons, ref, ...) Builder
Three blocks: vouchers by shop × series (last 4 digits of the reference; that series is the nominal code; narrative 'PIF donations redeemed'; R=4), the contra by shop × full reference (nominal 2710, 'Voucher - <ref>', R=5), and coupons by code (nominal 5000, 'Coupon - <code>', outlet from reference, R=5).

Checks and output

balance_and_checks(...) Validator
Fills report['checks']:
  • Side A (all J where R is 4 or 2) must equal side B (R is 5 or 1)
  • Items must equal payments per sale
  • No MISC left
  • No voids with value
  • No multi-payment sales left
  • Zettle rows all matched
  • Coupon file total equals the till's coupon total
Returns True only if all pass.
PTF_HEADERS + rows_to_df(rows) Formatter
Converts the H..Z dictionaries into the 19-column CSV layout, rounds money to 2dp, formats dates dd/mm/yyyy.

Recipes for common changes

Copy-paste instructions for everyday edits
Change the £10 cash-difference review threshold Code
File: pipeline_core.py, inside build_banking_table. Find if abs(difference) > 10: and change the 10. Also reword the message in the line below if you like (it's just text in an f-string).
Add a shop No code
In reference.json, inside "shop_cost_centre", add a line like "CG-WYT01": "A52", (note the comma). That alone gives it the 8 daily PTF 2 lines, its cost centre everywhere, and its department.
Add or re-map a coupon code No code
In reference.json, inside "coupon_outlet", add "NEWCODE": "Cafe - Mess",.
Change which department a shop prefix gets Code
pipeline_core.py, dept_of — four short lines, edit the prefixes/labels.
Reword a journal narrative Mixed
For PTF 2 lines, edit the description text in reference.json's ptf2_row_types (no code). For PTF 3, the texts 'PIF donations redeemed', 'Voucher - ', 'Coupon - ' are literal strings inside build_ptf3_rows. For the café blank label, run with --blank-desc "Open Food" or change the default in run_day.
Change a nominal code Code
PTF 2 codes live in reference.json (ptf2_row_types → bank / code). PTF 1 codes (4150 / 2710 / 5000) are in eval_ptf1_row. PTF 3's 2710 and 5000 are in build_ptf3_rows.
Change the penny-fix limit (currently 5p) Code
pipeline_core.py, inside clean, find > 0.05 near the penny section.
Change which payment method keeps the original Sale ID in a split Code
Edit MOVE_PRIORITY at the top of pipeline_core.py — higher number keeps the ID. Don't demote CARD/IZETTLE below the others: the card part must keep the original ID or Zettle matching breaks.
Make something block exports / stop it blocking Code
Find where it's appended and switch the list: report['manual_review'].append(...) blocks, report.setdefault('warnings', []).append(...) doesn't.
Change folder or file names Code
daily_runner.py (INCOMING, OUTPUT, ARCHIVE, and the find_one patterns) and, for the export file names, the f'{base}_{name}_export.csv' line in run_day.
Change the £1-style tolerance used everywhere Code
That's TOL = 0.005 (half a penny) at the top of pipeline_core.py. Think twice — it's used in the balance checks too.
6

Golden rules

Things NOT to change
1. Never edit PTF_HEADERS or the H..Z letters
They are your accounting import format. Rename one and the import breaks.
2. Never rename the input column names the readers look for
'Sale ID', 'Payment Method', 'Payment Amount', 'Outlet Tag', 'Total', 'Shop_Code', 'Cash_Banked', … — unless the source files really changed.
3. Don't change the R (SYSTraderTranType) logic
4/5/1 decide which side of the ledger a line sits on. Get one wrong and days stop balancing.
4. Keep J values positive
The sign information lives in R, not in J.
5. Don't weaken the balance check to "make a day pass"
If a day won't balance, the data is telling you something — the run report says what.
6. Keep reference.json valid JSON
Double quotes around names and values, commas between entries, no comma after the last entry in a block. If a run fails right after you edited it, it's almost always a missing or extra comma.
7. One change at a time
Then test (Part 7), then the next change.
7

How to test any change safely

A reliable workflow for every edit

Keep a "known good day" — a set of inputs whose correct outputs you trust (your archive/ folders are perfect for this: each holds the exact inputs for that date, and output/<date>/ holds what they should produce).

After any edit:

1
Copy a known good day's inputs from archive/<date>/ back into incoming/ and double-click Run Daily Reconciliation.
2
It should say BALANCED with the same totals as before.
3
Compare the new exports with the old ones:
Terminal
python3 validate_exports.py --any-order output/<date>_run2 \
    output/<date>/*_PTF1_export.csv \
    output/<date>/*_PTF2_export.csv \
    output/<date>/*_PTF3_export.csv

"VALIDATION PASSED" = your change altered nothing it shouldn't.

(If your change was meant to alter the output — a reworded narrative, say — the diff will list exactly the cells that changed, so you can confirm it's only what you intended.)

4
Only then process new days with the changed scripts.
If anything goes wrong

Restore your BACKUP copy of the file, re-run the known good day to confirm you're back to normal, and try again in smaller steps. And of course — bring the error message back to Claude and we'll fix it together.
